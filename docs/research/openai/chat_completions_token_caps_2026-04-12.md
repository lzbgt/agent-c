Notes:
- The Chat Completions streaming response model documents `stream_options: {"include_usage": true}` for usage chunks in streaming responses.
- The same reference describes `ChatCompletionStreamOptions.include_usage` as causing an additional usage chunk before `data: [DONE]`; it also notes that interrupted streams may miss the final usage chunk.
- The API reference page is generated by Stainless and the local HTML artifact is the durable source snapshot for this implementation note.
- For provider-side output caps, this repo uses `max_completion_tokens` as the preferred current Chat Completions cap and preserves `max_tokens` only when the caller already supplied the legacy/provider-compat field. This avoids sending both fields by default.

Implementation consequence:
- Workflow `max_total_tokens` now clamps each pending run request to the remaining workflow token budget before the provider call.
- When no explicit per-run cap exists, the workflow engine sets `max_completion_tokens` to the remaining budget.
- If the caller already supplied `max_completion_tokens`, it is reduced to the remaining budget.
- If the caller supplied only legacy `max_tokens`, that field is reduced instead of adding a second cap field.
